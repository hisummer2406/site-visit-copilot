# 02 · 方案设计讨论稿

> 版本 v0.1 · 2026-09-15 · 状态：讨论稿，待团队评审
> 前置阅读：[01-需求背景与问题定义.md](01-需求背景与问题定义.md)

## 1. 设计原则

1. **零录入负担**：不要求任何人填表、选项目、打标签；采集端只是"在群里发消息"。
2. **AI 出草稿，人只确认**：结构化、纪要、对比全部 AI 生成，人的角色是审核而非录入。
3. **字段最小可用**：先 8–10 个核心字段，跑两批再扩；一次定全了团队记不住、AI 也填不准。
4. **schema 面向聚合设计**：字段从第一天起按可跨客户/跨项目聚合的标准设计（为数据对标网络保留期权）。

## 2. 四段式流水线

```
考察前 → 考察中 → 考察后 → 沉淀复用
背景包    随手采集   结构化加工  资产库
```

| 阶段 | 内容 | 说明 |
|---|---|---|
| 考察前 | 自动生成背景包 | 该项目历次记录 + 同类项目对标 + 本次关注点清单；硬指标由公开数据自动预填 |
| 考察中 | 群里随手发 | 照片/语音/文字，自动归入批次，不填任何表 |
| 考察后 | AI 加工 | 多模态理解 → 抽取统一字段 → 生成考察纪要 → 一人点确认 |
| 沉淀复用 | 资产库 | 项目+产品标签双轴，同类横向对比，下次考察自动调用 |

## 3. 枢纽设计：考察批次

**「考察批次」是整套方案的枢纽**，一个设计同时解决采集断层与复用断层：

- 出发前在群里说一句"周三去看 XX 项目的四代宅"→ 机器人建批次卡片
- 成员发的所有照片、语音、文字自动归入本批次，无人需要选项目
- 批次关闭时自动出纪要
- 照片定位不靠打标签，靠**批次 + 消息上下文推断**

## 4. 三层落地架构

```
企微考察群（采集）→ 考察助手智能体（加工）→ 企微智能表格（资产）
```

| 层 | 职责 | 要点 |
|---|---|---|
| 企微考察群 | 采集 | 照片/语音/文字随手发；不填表、不选项目；自动归批次 |
| 考察助手智能体 | 加工 | 按批次归集素材 → 图像与语音理解 → 抽取统一字段 → 生成结构化纪要。**注意：企微智能表格无多模态理解能力，加工必须在智能体侧完成** |
| 企微智能表格 | 资产 | 考察项目库主表 + 素材明细子表；按产品标签横向对标；下次考察自动调用 |

智能体实际运行在 WorkBuddy 侧（或其他具备多模态能力的 Agent 平台），加工结果写回智能表格。

## 5. 字段体系（v0.1 草案，待确认）

| 分组 | 字段 | 说明 |
|---|---|---|
| 归属 | 项目名称、城市/区域、开发商、考察日期、参与人 | 基础定位，AI 从群消息自动补 |
| 分类 | **产品标签（多选）** | 四代宅/改善/刚需/TOD/康养/低密——横向对标的前提 |
| 硬指标 | 占地、容积率、主力户型、均价、去化 | 可量化对比项，AI 抽取 + 人工校验；客观数据可由背景包预填 |
| 主观判断 | 亮点、问题与风险、可借鉴点、竞品对标 | AI 从照片和对话提炼，人确认 |
| 原始追溯 | 素材链接、考察批次 | 每条结论可回查原始照片与对话 |

## 6. 三步走（按数据依赖排序，非按痛点排序）

| 顺序 | 做什么 | 依赖 | 理由 |
|---|---|---|---|
| ① 考察后整理 | 群聊记录合并转发 → AI 解析 → 写表 → 出纪要 | 无（现成链路） | 三个痛点里占两个；是后两步的数据来源；**零开发可跑** |
| ② 考察前背景包 | 自动生成背景包 + 关注点清单 | 库里有 2–3 批数据 | 空库的背景包是空壳 |
| ③ 考察中实时采集 | 企微自建应用 + 消息回调 | IT 配合 | 投入最大，验证价值后再上 |

### 轻量版（第①步）执行形态

考察结束后，将企微考察群的聊天记录**合并转发**给智能体（WorkBuddy 已具备该解析链路，含图片与在线资源），由其：

1. 解析照片、语音、文字与转发的在线文档
2. 按字段体系抽取结构化数据
3. 写入企微智能表格（主表一行/项目，子表明细/素材）
4. 生成本批次考察纪要（初稿），负责人确认后归档

## 7. 硬骨头（预研项）

| 事项 | 风险 | 对策 |
|---|---|---|
| 冷启动 | 新库是空的，前两批没有对标体验差 | 先把既有表格/照片批量灌一次 |
| 语音转写 | 现场 ASR 准确率未验证 | 第①步试点时实测；不达标则提示"现场优先文字/拍照" |
| 长期维护 | 考察频次低则重投入易荒废 | 以轻量版起步，验证后再扩 |
